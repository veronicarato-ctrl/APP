# Travel Guide app, working rules for Claude Code

Read `SPEC.md` (French, the product specification) before any change. The reference prototype is
`guiao-viagem-brasil.jsx`; `bresil-2026.jsx` is excluded and must not be used as a source.

## Non-negotiable principles (SPEC section 2)

1. **Single source of truth.** Every screen is derived from one data model (`src/model/types.ts`).
   A fact (reference, address, date) exists in one place only. Weekdays are computed from dates, never stored.
2. **AI proposes, the user decides.** No AI change is applied without explicit validation, operation by operation.
3. **Confirmed bookings are untouchable.** Linked slots are locked (🔴) and cannot be edited, moved or deleted
   until the user unlocks the booking.
4. **Nothing is deleted or moved to another day without confirmation**, and everything goes to the history log.
5. **Every piece of information states its nature**: verified (source and check date), estimated,
   recommendation, or proposed by the AI. A price is confirmed, estimated or a range.
6. **No invented facts.** Flight times, prices, addresses, entry rules, health data or transport frequencies
   without a source stay empty and become a question.
7. **Priority order of any proposal**: safety, legal obligations, confirmed bookings, must-dos, budget,
   preferences, pace, geographic coherence, optimisation.

## Never (SPEC section 13)

1. Hard-code trip data in components (it lives in IndexedDB, seeded from `src/data`).
2. Let the AI rewrite the trip or write directly to the database.
3. Invent or complete a factual item without a source.
4. Duplicate information across collections.
5. Use localStorage as main storage (only per-device conveniences such as appearance).
6. Expose the API key in the frontend.
7. Generate a KML or Google My Maps export.
8. Send a postcard or share a position without an explicit user action.
9. Build a GPS, booking engine, social network or universal translator.
10. Change design, language or stack without asking.
11. Show an emergency number, embassy address or safety advice without an official source and check date.
12. Hard-code a colour in a component, or leave a black or brown background. Use the tokens in `src/index.css`.

## Conventions

- UI, code, comments and this file are in English. UI strings live in `src/i18n/en.ts`; never inline them.
- Stored free text is a `Text` (`{ text, lang }`). Imported Brazil data keeps `lang: "pt"` and is never auto-translated.
- Colours: general tokens never change; identity and region colours come from `Trip.theme` (SPEC section 10).
- IDs are UUIDs. Imported records use deterministic UUID v5 from their prototype key (`src/lib/ids.ts`).
- Times are local to the place; every place carries an IANA zone.
- The Brazil seed (`src/data/brazil-2026.prototype.json`) is generated by `npm run extract-seed`, never edited by hand.

## Commands

- `npm run dev` start the app, `npm test` run all tests, `npm run typecheck`, `npm run build`.
- Sync tests (`supabase/*.test.ts`) run the real SQL migrations in embedded PostgreSQL (PGlite);
  any change to `supabase/migrations` or `src/sync/merge.ts` must keep both merge rules identical.
- Supabase and Vercel setup for the user: `SETUP.md`. Only public settings (`VITE_SUPABASE_URL`,
  `VITE_SUPABASE_ANON_KEY`) go to the frontend; never a service_role/secret key.
- Write the test before considering a rule done. The Brazil seed must produce exactly two errors on
  20 December and three warnings (`src/engine/rules.test.ts`).

## Roadmap

- The app is general-purpose: any trip, several trips per account. Brazil 2026 is only the first real test
  and a loadable example trip (`loadExampleTrip`), never hard-wired. Phases 1 to 7 are the personal version tested on it. Commercialisation is phase 8,
  after the trip (SPEC section 16). Do not start phase 8 work before then, but never make a choice in
  phases 1 to 7 that would block it (i18n, data outside code, per-trip theme, UUIDs).
- Target UI languages for phase 8: en, fr, es, pt (pt-PT first), zh. All UI text must go through i18n.

## Working method

- One commit per coherent step. Show the result at the end of each phase and wait for approval before the next.
- When the user reports an error: stop, re-read all related context, then fix.
